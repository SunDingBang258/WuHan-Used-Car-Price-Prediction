## 0. 一分钟看懂

```
che168.com 武汉站的二手车列表页
        ↓  爬虫
   4128 条原始记录(2 个来源合并)
        ↓  清洗 + 补派生列
     3408 条  = 数据版本 v1
        ↓  车系名规范化 + 分组过滤
     3141 条  = 数据版本 v2   ← DVC 管理, 训练实际用的就是它
        ↓  特征工程(12 列 → 11 个模型输入)
  HistGradientBoostingRegressor
        ↓  5 折交叉验证
   MAPE 14.12%   MAE 3.00 万   R² 0.739
        ↓  cloudpickle 序列化
   app/model.joblib (1.5 MB)  →  用户在网页填表 → 价格
```

**用户看到的东西**：一个表单（品牌、车系、车龄、里程、是否过户…），提交后返回一个估价，比如「33.67 万」。

**后台做的事**：根据品牌/车系查一张静态对照表补出 3 个统计特征，拼成 11 维向量，喂给模型，输出一个数。

## 1. 问题定义

### 1.1 这是一个什么任务

| 维度 | 内容 |
|---|---|
| 输入 | 一辆二手车的属性（品牌、车系、车龄、表显里程、是否 0 次过户…） |
| 输出 | 一个连续数值：售价（万元） |
| 任务类型 | **回归**（不是分类） |
| 评价指标 | **MAPE**（平均绝对百分比误差），辅助看 MAE / RMSE / R² |

### 1.2 这个任务难在哪

**难点一：目标跨了三个数量级。**

实测 v2 数据的售价分布：

| 价格区间 | 条数 | 占比 |
|---|---|---|
| 0–5 万 | 528 | 16.8% |
| 5–10 万 | 851 | 27.1% |
| 10–20 万 | 1005 | **32.0%** |
| 20–50 万 | 589 | 18.8% |
| 50–100 万 | 115 | 3.7% |
| 100 万+ | 53 | 1.7% |

最低 0.58 万，最高 588.80 万 —— **差 1000 倍**。

后果：
- 用 MSE 当损失，模型会**全力照顾贵车**（因为误差平方后贵车的贡献压倒性大），便宜车全预测歪。
- 所以生产版把损失换成 **MAE（绝对误差）**。见 §8.3。

**难点二：车系有 279 种。**

品牌只有 30 个，车系却有 279 个。每增加一种类别取值就多一份要学的参数，样本量跟不上 → 过拟合。这是 §5.3 和 §8.4 要解决的核心问题。

**难点三：价格靠的是"这辆车在市场上的相对位置"。**

同样 3 年 5 万公里，宝马 X5 和五菱宏光价格差 20 倍。光靠「车龄 + 里程」两个数字学不出来，
必须让模型知道「这辆车的身份」。这就是 §5.4 那三个统计特征的来源。

## 2. 数据从哪来

### 2.1 两个抓取来源，为什么要两个

| 来源 | 文件 | 条数 | 内容 | 权威性 |
|---|---|---|---|---|
| **A** | `data/爬虫/che168_wuhan_brands.csv` | 3222 | 按**品牌页**逐个品牌抓取 | **品牌名来自 URL，权威** |
| **B** | `data/数据处理/che168_wuhan_cars.raw.csv` | 2239 | 早期按**列表页**混合抓取（31 列） | 品牌名有缺失 |

为什么需要两个：

- **来源 B 先抓**，覆盖广但品牌名经常缺（列表页上品牌名要靠猜）。
- **来源 A 后补抓**，走品牌页所以品牌名绝对正确，但只覆盖了 30 个品牌。

合并策略：**按 `车源ID` 去重，A 优先**（同一辆车两边都有时用 A 的品牌名）。
再给 B 里那些品牌名为空的行，用 A 建立的 `brandid → 品牌名` 映射补上。

> A + B 合并后 **4128 条**。

### 2.2 一条记录有哪些字段

原始 20 列（`KEEP_COLUMNS`）：

| 类别 | 字段 |
|---|---|
| 标识 | `车源ID` `详情页` `品牌ID` `车系ID` |
| 车辆 | `车型` `品牌名称` `车系名称` `表显里程(万公里)` `车龄(年)` |
| 价格 | `售价(万元)` ← **预测目标** `新车指导价(万元)` `品牌平均折价率(%)` `车系平均折价率(%)` `车系历史中位价(万元)` |
| 车况 | `年均里程(万公里/年)` `0次过户` `原厂质保` `准新车标记(站点)` |
| 交易 | `发布时间` |
| 媒体 | `封面图` |

这 20 列里：
- **7 列只作展示**：`车源ID` `详情页` `车型` `品牌名称` `车系名称` `新车指导价(万元)` `封面图`
- **1 列是目标**：`售价(万元)`
- **12 列是候选特征**，其中 11 个真正进模型（特征清单见 `ml/train.py` 顶部的 `CATEGORICAL` / `NUMERIC` / `LOOKUP_KEYS`）

## 3. 数据清洗：从爬虫到 v1

`ml/data_pipeline.py` 做六件事。**每一步都对应一个具体的数据问题**。

### 步骤 1：合并两个来源

```
A(3222) + B(2239) → 按车源ID去重, A 优先 → 4128 条
```

**为什么**：两个来源有重叠，不去重会让某些车被数两遍，统计特征（折价率、中位价）就偏了。

### 步骤 2：丢掉不可靠的行

| 丢弃条件 | 条数 | 为什么 |
|---|---|---|
| `品牌名称` 为空 | −712 | 品牌是核心特征，没有就没法用 |
| `车龄(年)` 为空 | −7 | 车龄是最重要的数值特征之一 |
| `年均里程 > 10.0 万/年` | −1 | 数据自相矛盾（可能里程或车龄录错） |

结果：3416 → 3409 → **3408 条**。

**为什么用"丢"而不是"填"**：这 719 条缺的是关键字段，填一个猜的值等于给模型喂噪声；
样本量够（3400+），丢掉不心疼。

### 步骤 3：补派生列

| 派生列 | 算法 | 为什么需要 |
|---|---|---|
| `车系名称` | 从 `车型` 字符串里切出来 | 194 条车系名为空，`车型` 里其实有 |
| `年均里程(万公里/年)` | `表显里程 ÷ 车龄`（车龄为 0 时取里程本身） | 同样 10 万公里，1 年车和 8 年车完全不是一回事 |

### 步骤 4：分组过滤（→ v2 才做）

车系名称规范化、品牌/车系样本量过滤。详见下一节 §4。

> **注意**：这一步是 v1/v2 的分界。

### 步骤 5：补三个目标编码特征

| 特征 | 算法 | 为什么需要 |
|---|---|---|
| `品牌平均折价率(%)` | `(新车指导价 − 售价) / 新车指导价 × 100`，按品牌取中位数 | 让模型知道"这个品牌保值吗" |
| `车系平均折价率(%)` | 同上，按车系算 | 让模型知道"这个车系保值吗" |
| `车系历史中位价(万元)` | 按车系取售价中位数 | 让模型知道"这个车系大概多少钱一辆" |

**为什么用中位数而不是平均数**：售价是长尾（最高 588 万），平均数会被极值拉飞。
中位数对异常值不敏感。

**为什么必须放在步骤 4 之后**：这三列都是拿**售价**（预测目标）算出来的。
如果在过滤之前算，被删掉的那 267 行仍然会参与中位数，结果就是
CSV / `app/reference.json` 里存的值 ≠ 训练时用过滤后数据重算的值，
等于训练和应用喂给模型的特征分布不完全一样（train/serve skew）。

### 步骤 6：写出 CSV 与对照表

```python
# CSV 是 3 行表头: 标题行 + 维度行 + 真正的列名行(train.py 用 header=2 读)
```

只保留 `KEEP_COLUMNS` 20 列 → `data/che168_wuhan_cars.csv`，
再把 品牌/车系 → ID + 查表特征 导出成 `app/reference.json`。

**为什么要有对照表**：应用的表单下拉和提交查表都靠它，用户选「宝马X5」
后台要能立刻查出 `车系ID=6548, 车系折价率=42.89, 车系中位价=39.98`
三个模型特征 —— 不需要带着全量数据去算。

## 4. v1 → v2：两个数据版本的区别

项目里维护**两个 DVC 版本**，同一个脚本产出，靠 `--v1` 开关区分。

### 4.1 总览

| | **v1**（第一版可用） | **v2**（当前，训练用） |
|---|---|---|
| 文件 | `data/che168_wuhan_cars_v1.csv` | `data/che168_wuhan_cars.csv` |
| DVC 指针 | `data/che168_wuhan_cars_v1.csv.dvc` | `data/che168_wuhan_cars.csv.dvc` |
| **DVC md5** | `d2b80f5b67d653d7abe741ff21e7fb1c` | `4439910deb63db4bc4ec0646389c1962` |
| 字节 | 861,865 | 793,525 |
| **行数** | **3408** | **3141** |
| 品牌数 | 30 | 30 |
| **车系ID 数** | **475** | **279** |
| **车系名称种数** | **492** | **279** |
| 一个车系ID 对应多种写法 | **15 个 ID** 有问题 | **0 个** |
| 车系样本量 min / median / max | **1** / 3 / 88 | **3** / 7 / 88 |
| 样本量 < 3 的车系 | **196 个** | **0 个** |
| 售价 min / median / max | 0.58 / 11.38 / 588.80 万 | 0.58 / 11.78 / 588.80 万 |
| 生成命令 | `python ml\data_pipeline.py --v1` | `python ml\data_pipeline.py` |

从 v1 到 v2 只做了**两件事**，行数减少 267 条（7.8%）。

### 4.2 差异一：车系名称规范化

**问题**：`车系ID` 是爬虫给的一个数字编号，`车系名称` 是从 `车型` 文本里切出来的字符串。
同一辆车系，不同车源的写法可能不同：

```
车系ID = 12345
   ├── "揽胜极光进口"    出现 4 次
   ├── "揽胜极光(进口)"   出现 2 次
   └── "揽胜极光"         出现 1 次
```

v1 里 **475 个车系ID 对应 492 种名称**，有 15 个 ID 的写法不唯一。

**为什么这是问题**：

1. `app/reference.json`（应用的下拉框数据源）是**以车系名称为键**的。同一个车系在下拉框里会出现两三个选项，用户不知道该选哪个。
2. 用户选了「揽胜极光(进口)」，查表时只能匹配到那 2 条样本算出来的统计量 —— 样本量本来就只有个位数，再被拆成三份，`车系平均折价率` 几乎是这一两条车自己的值。

**v2 的做法**：对每个 `车系ID`，只保留**出现次数最多的那种写法**（`Counter.most_common(1)`）。

结果：492 种名称 → **279 种**，ID 和名称严格一一对应。

### 4.3 差异二：分组过滤

**问题**：v1 里有 196 个车系只有 1–2 条样本（最少的只有 1 条）。

**为什么这是问题（这是最要命的一点）**：

`车系平均折价率` 是通过下面的公式算出来的：

```
折价率 = (新车指导价 − 售价) / 新车指导价 × 100
                          ↑
                      这是预测目标
```

也就是说，**目标变量被用来构造特征**。这种做法叫**目标编码（target encoding）**，
在业界很常用，但有个致命前提：**计算统计量用的样本，不能是评估时要预测的那些行**。

如果一个车系只有 1 条样本，那么它自己的 `车系平均折价率` **精确地等于它自己的折价率** ——
模型不需要学任何东西，直接把特征抄出来就行。这就是**目标泄漏（target leakage）**，
训练指标会漂亮得离谱，上了线立刻崩。

**v2 的做法**：把样本量不足的组整组删掉。

```python
MIN_BRAND = 5     # 品牌至少 5 条
MIN_SERIES = 3    # 车系至少 3 条
```

而且是**反复过滤到稳定**：

```python
while True:
    size = len(merged)
    删掉 品牌 < 5 的行
    删掉 车系 < 3 的行
    if len(merged) == size:   # 这一轮没删掉任何东西 → 稳定了
        break
```

**为什么要循环**：删掉一些行之后，本来够 5 条的品牌可能剩 4 条了，需要再删一轮。

结果：
- 车系ID：475 → **279**（正好删掉那 196 个小样本车系）
- 行数：3408 → **3141**（删掉 267 条）
- 所有车系最少 3 条，所有品牌最少 5 条

### 4.4 为什么两个版本都要留着

| 版本 | 用途 |
|---|---|
| **v1** | 数据版本演进的历史证据。做课程项目时用来回答"你做过哪些数据改进" |
| **v2** | 实际训练用的版本。`ml/train.py` 里的 `DATASET` 常量指向它 |

**这不是"留个旧的当备份"** —— 是数据版本管理（DVC）要求你**能回到任意一个历史版本**。
`git checkout <commit> -- data/che168_wuhan_cars.csv.dvc && dvc checkout` 就能精确还原。

## 5. 特征工程：12 列 → 11 个模型输入

### 5.1 完整特征表

| # | 特征 | 类型 | 处理方式 | 为什么需要它 |
|---|---|---|---|---|
| 1 | `品牌ID` | 类别（30 值） | 类别特征，交给模型原生处理 | 品牌决定了基础价位和保值率 |
| 2 | `车系ID` | 类别（279 值） | **不进模型**，见 §5.3 | 身份由下面 #3 #4 #5 承载 |
| 3 | `品牌平均折价率(%)` | 数值 | 折内重算，见 §7 | 这个品牌整体保值吗 |
| 4 | `车系平均折价率(%)` | 数值 | 折内重算 | 这个车系整体保值吗 |
| 5 | `车系历史中位价(万元)` | 数值 | 折内重算 | 这个车系大概什么价位 |
| 6 | `表显里程(万公里)` | 数值 | 直接 | 里程是折旧的主要因素 |
| 7 | `车龄(年)` | 数值 | 直接（由 `上牌时间` 换算） | **最强单特征** |
| 8 | `年均里程(万公里/年)` | 数值 | 里程 ÷ 车龄 | 用车强度；同样里程下 1 年的车和 8 年的车不是一回事 |
| 9 | `0次过户` | 0/1 | 直接 | 过户次数少通常车况好 |
| 10 | `原厂质保` | 0/1 | 直接 | 还在保内的车溢价 |
| 11 | `发布时间序号` | 数值 | 距 2020-01-01 的天数 | 捕捉市场行情的时间漂移 |
| 12 | `准新车标记(站点)` | 0/1 | 直接 | 站点自己的判断，是个免费的先验 |

**加上 `品牌ID`，模型实际输入是 11 维**（12 个候选里去掉 `车系ID`）。

> `发布时间` → `发布时间序号`：模型只认数字，把日期转成"距某天多少天"是最简单的编码方式，
> 且天然保留了时间顺序（不需要 OneHot）。

### 5.2 为什么不用 OneHot 编码

`品牌ID` 有 30 个取值，OneHot 会产生 30 列稀疏特征。问题：
- 30 列里每行只有 1 个 1，信息密度极低；
- 新增一个品牌就要改模型结构；
- OneHot 后的列和数值特征混在一起，树模型切分效率变低。

**做法**：直接告诉 sklearn「这一列是类别特征」，让 `HistGradientBoostingRegressor` 内部处理。

```python
categorical_features=["品牌ID"]
```

它内部用排序 + 分箱的方式处理类别，效果接近 OneHot 但没有维度爆炸。

### 5.3 为什么 `车系ID` 反而不能当类别特征

`HistGradientBoostingRegressor` 对类别特征有一个**硬限制：最多 255 个取值**。

而 v2 有 **279 个车系ID**，超出上限，sklearn 会直接报错。

三个备选方案：

| 方案 | 为什么不选 |
|---|---|
| 把 279 个车系合并成更少的组 | 丢失信息，且"怎么合"本身是个不可靠的人工判断 |
| 用 `车系名称` 做目标编码 | 做了 —— 就是 `车系平均折价率` 和 `车系历史中位价` |
| 把 ID 当数值特征 | **错的**：ID 是随机编号，`12345 + 1` 没有任何意义 |

**最终方案**：`车系ID` 只作为**标识列**存在（用于查表和生成 `reference.json`），
不进模型。它的"身份信息"由三个目标编码特征承载（#3 #4 #5）——
这就是"用统计量代替 ID"的经典做法。

### 5.4 训练用的是 ndarray，不是 DataFrame

```python
def build_x(df, use_lookups, tables, fallback):
    ...
    return x   # numpy.ndarray, 不是 DataFrame
```

**为什么**：如果训练时传 DataFrame，sklearn 会记录 `feature_names_in_`，
之后用 ndarray 推理就会警告：

```
UserWarning: X does not have valid feature names, but OrdinalEncoder was fitted with feature names
```

这个警告在训练时无害，但**应用推理时每一行日志都会刷一遍**，而且意味着训练/推理的输入路径不一致。

**做法**：
1. 训练统一用 ndarray（按 `feature_names()` 给出的顺序拼）；
2. 模型签名手工构造，把列名写进去。

```python
signature = ModelSignature(
    inputs=Schema([ColSpec("double", n) for n in names]),   # ← 列名在这里
    outputs=Schema([ColSpec("double", "price_wan")]),
)
```

这样既没有警告，模型元数据里又能看到每列的名字。

## 6. 目标编码的泄漏陷阱（这一节最重要）

### 6.1 问题

`品牌平均折价率` 是用下面的数据算的：

```
折价率 = (新车指导价 − 售价) / 新车指导价 × 100
```

而 `售价` 就是**我们要预测的东西**。

### 6.2 错误做法

```python
# ❌ 全量算一次, 然后交叉验证
tables = lookup_tables(df)          # 用了全部 3141 行
for train_idx, valid_idx in kfold.split(df):
    x_train = build_x(df.iloc[train_idx], tables)   # 用到了 valid 行的售价!
    x_valid = build_x(df.iloc[valid_idx], tables)
```

验证集里每一行的 `品牌平均折价率`，都是**包含它自己**算出来的。模型只要记住这个特征就赢了一半。

结果：验证 MAPE 可能显示 8%，实际上线 20%+。

### 6.3 正确做法：折内重算

```python
# ✓ 每一折只用训练部分重新算统计量
for train_idx, valid_idx in kfold.split(df):
    train = df.iloc[train_idx]
    tables = lookup_tables(train)              # ← 只用 train 算
    x_train = build_x(train, tables)
    x_valid = build_x(df.iloc[valid_idx], tables)   # valid 用 train 算出来的表
```

验证集的折价率**来自训练折的统计**，符合"用历史数据预测未来"的真实场景。

代码里 `cross_validate()` 就是这么写的，注释也标了「折内重算防泄漏」。

### 6.4 兜底值

验证折里可能出现训练折**完全没见过**的车系。这时查表查不到，用全局值兜底：

```python
fallback = {"品牌": 全局平均折价率, "车系": 全局平均折价率, "中位价": 全局中位价}
```

**为什么**：宁可给一个"平均水平"的猜测，也不能给 `NaN`（模型会直接崩）。

## 7. 模型选型

### 7.1 最终选择

```python
HistGradientBoostingRegressor(
    loss="absolute_error",
    learning_rate=0.06,
    max_iter=400,
    max_leaf_nodes=31,
    min_samples_leaf=20,
    l2_regularization=1.0,
    categorical_features=["品牌ID"],
)
```

### 7.2 为什么是梯度提升树（而不是别的）

| 候选 | 优点 | 为什么没选 |
|---|---|---|
| 线性回归 | 快、可解释 | 车龄和价格是**非线性**关系（前 3 年掉价快，后面平缓），线性拟合不了 |
| 随机森林 | 稳、不易过拟合 | 在**表格数据**上通常不如梯度提升；且不好处理类别特征 |
| 神经网络 | 表达力强 | 3141 条样本**太少**，神经网络会严重过拟合；调参成本高 |
| **梯度提升树** | 表格数据 SOTA、能处理类别、对缺失值友好、不需要标准化 | **选它** |

再具体到 `HistGradientBoosting`（而不是 `GradientBoosting`）：
- 用直方图分箱代替精确切分，**训练快 10 倍以上**；
- 原生支持 `categorical_features`；
- 原生支持缺失值（不用先填充）。

### 7.3 为什么 `loss="absolute_error"`（不是默认的 `squared_error`）

| 损失 | 优化目标 | 后果 |
|---|---|---|
| `squared_error`（MSE） | 均方误差 | 588 万那台车的误差平方是 5 万那台车的 **10000 倍**，模型会为了它牺牲所有便宜车 |
| `absolute_error`（MAE） | 平均绝对误差 | 每个样本权重相同，不会被极值绑架 |

而我们的评价指标是 **MAPE（百分比误差）**，它本身就是**相对误差** —— 和 MAE 同向。
`loss=MAE` 让训练目标和评价指标对齐。

**实测差距**：baseline 用 `squared_error` 得到 MAPE 51.38%，tuned 用 `absolute_error`
再加上三个目标编码特征得到 14.12%。**不能完全归因于 loss**，但 `absolute_error` 是必要的一环。

### 7.4 为什么 `learning_rate=0.06` + `max_iter=400`

经验规律：**学习率 × 迭代次数 ≈ 常数**（这里 0.06 × 400 = 24）。

| 组合 | 效果 |
|---|---|
| `lr=0.1, iter=100`（baseline） | 快，但欠拟合 |
| `lr=0.06, iter=400`（tuned） | 慢一点，拟合更充分，泛化更好 |

**为什么不用更小的 lr**：0.01 × 2400 会更准一点，但训练时间线性增长，
在 3141 条样本上收益递减。0.06/400 是本地实测的性价比点。

### 7.5 为什么 `l2_regularization=1.0`

应对过拟合。279 个车系、3141 条样本，平均每个车系 11 条 —— 模型很容易把某几个车系"背下来"。
L2 正则让叶子节点的取值不要走极端。

`min_samples_leaf=20` 是另一道保险：一个叶子至少 20 条样本，防止模型为了 3 条样本单独开一个叶子。

## 8. 交叉验证设计

### 8.1 为什么是 5 折（不是留出法）

留出法（比如 80% 训练 / 20% 测试）有两个问题：
- 3141 条样本，切 20% 只有 628 条验证，**指标波动大**（换一次随机种子结果差几个点）；
- 训练只用 80% 数据，浪费。

5 折交叉验证：每一折都当一次验证集，最后平均 —— 指标更稳，且每个样本都被评估过一次。

```python
N_SPLITS = 5
KFold(n_splits=5, shuffle=True, random_state=42)
```

`random_state=42` 固定，保证**每次跑结果一致**（可复现性）。

### 8.2 为什么不做"冷启动"评估

我另外跑过 `GroupKFold`（按车系分组，保证验证集里的车系训练时从没见过），结果：

```
冷启动 MAPE ≈ 54.8%    R² ≈ 0
```

**意思是：遇到没见过的车系，模型基本等于瞎猜。**

**为什么可以接受**：因为应用的**表单只让用户从下拉框选已知车系**。
`app/reference.json` 里只有 279 个车系，用户选不到别的。
所以"没见过车系"这个场景在业务上不存在。

这个取舍要在文档里说清楚 —— 换了业务场景（比如允许自由输入车系），模型就不能用了。

### 8.3 逐折结果都记录

每次训练会 log 一张 `cv_folds.json`：

| fold | MAPE | RMSE | MAE | R² |
|---|---|---|---|---|
| 1–5 | 每折一行 | | | |
| 均值 | **14.12%** | 13.49 万 | 3.00 万 | 0.739 |

**为什么要逐折记录**：只看均值会掩盖"某一折特别差"。逐折看能发现数据分布不均的问题。

## 9. 两个实验与结果

### 9.1 baseline（对照组）

配置（`ml/train.py` 里的 `BASELINE` 常量）：

```python
BASELINE = {
    "use_lookups": False,          # 不用三个目标编码特征
    "loss": "squared_error",       # sklearn 默认
    "learning_rate": 0.1,
    "max_iter": 100,
    "l2_regularization": 0.0,
    "save_to_app": False,          # 不覆盖生产模型
}
```

**特征数 8 个**（11 − 3 个目标编码特征）。

### 9.2 tuned（生产版）

```python
TUNED = {
    "use_lookups": True,           # 加上三个目标编码特征
    "loss": "absolute_error",
    "learning_rate": 0.06,
    "max_iter": 400,
    "l2_regularization": 1.0,
    "save_to_app": True,           # 训练完覆盖 app/model.joblib
}
```

**特征数 11 个**。

### 9.3 结果对比

| | baseline | **tuned** | 改善 |
|---|---|---|---|
| 特征数 | 8 | **11** | +3 个目标编码特征 |
| **MAPE** | 51.38% | **14.12%** | **−37.3 个百分点（降 72.5%）** |
| RMSE | 19.78 万 | **13.49 万** | −6.29 万 |
| MAE | 7.97 万 | **3.00 万** | −4.97 万 |
| R² | 0.429 | **0.739** | +0.310 |

**怎么读这个对比**：

MAPE 从 51% 降到 14%，主要贡献来自**三个目标编码特征** —— 因为 baseline 的模型
根本不知道"这个车系大概值多少钱"，只能靠车龄/里程盲猜。
`loss` 从 MSE 换成 MAE 有次要贡献，超参调整贡献最小。

> 这也是为什么 `ml/README_experiments.md` 里认定 tuned 是生产版本：
> MAE 3.00 万意味着"平均每个车估错 3 万"，对于一个 0.58–588 万的价格区间来说是可用的。

### 9.4 怎么复现这两个实验

```powershell
# 都写在 ml/train.py 顶部的「配置区」里, 改一行切换
#   CONFIG = BASELINE  → 跑对照组
#   CONFIG = TUNED     → 跑生产版
.\.venv\Scripts\python.exe ml\train.py
```

## 10. 指标解读（诚实版）

### 10.1 为什么主指标是 MAPE

| 指标 | 含义 | 为什么用它 / 不用它 |
|---|---|---|
| **MAPE** | 平均绝对百分比误差 | **主指标**：业务上关心"估高了 10% 还是 100%"，相对误差更直观 |
| MAE | 平均绝对误差（万元） | 辅助：能换算成"平均估错几万"，好向非技术同事解释 |
| RMSE | 均方根误差 | 辅助：对极值更敏感，用来发现"是不是有几台车错得离谱" |
| R² | 拟合优度 | 辅助：0.739 表示解释了 73.9% 的方差 |

**MAPE 的缺点**：售价接近 0 时会被放大（除以一个很小的数）。数据集里最低 0.58 万，
所以这个问题**存在但可控**。

### 10.2 误差分布

| 统计量 | 值 |
|---|---|
| 中位数 APE | **9.32%** |
| 75 分位 APE | 17.6% |
| 90 分位 APE | 30% |

**解读**：一半的车误差在 9.3% 以内，但最差的 10% 误差超过 30%。

### 10.3 分价位段的表现

| 价位 | MAE | MAPE |
|---|---|---|
| 0–5 万 | 0.44 万 | 22.4% |
| 10–20 万 | 1.18 万 | **11.6%**（最好） |
| 100 万+ | 25.86 万 | 27.7% |

**两个反直觉的现象**：

1. **便宜车绝对误差最小（0.44 万），百分比误差却最大（22.4%）**
   —— 因为分母小。估错 0.44 万，对 2 万的车是 22%，对 100 万的车是 0.4%。

2. **贵车绝对误差最大（25.86 万）**
   —— 因为 100 万+ 只有 53 条样本（1.7%），模型没学够；
   而且超跑/豪华车的价格受配置、车况、稀缺度影响巨大，光靠这 11 个特征学不出来。

**所以这个模型的定位是**：主流价位（5–50 万，占 78.9%）的快速估价参考，
不是豪华车的精准定价工具。

## 11. 从无到有：完整实现步骤

按这个顺序做，每一步都说明为什么在这个位置。

### 阶段一：数据

| # | 做什么 | 命令 / 文件 | 为什么在这一步 |
|---|---|---|---|
| 1 | 爬虫抓数据 | `data/爬虫/` `data/数据处理/` | 一切的前提 |
| 2 | DVC 初始化 | `dvc init` | 数据要先能被版本管理 |
| 3 | 配 Azure 远程 | `.dvc/config` → `azure://dvc` | 大文件不能进 git |
| 4 | 合并 + 清洗 | `python ml\data_pipeline.py` | 得到可用的 v2 |
| 5 | 生成 v1 | `python ml\data_pipeline.py --v1` | 保留演进历史 |
| 6 | DVC 跟踪两版 | `dvc add data/*.csv` | 生成 `.dvc` 指针文件 |
| 7 | 推数据到远程 | `dvc push` | 别人 clone 后能 `dvc pull` 还原 |
| 8 | 导出应用对照表 | （第 4 步顺带做的）→ `app/reference.json` | 应用表单和查表都靠它 |

**为什么数据在最前面**：模型的所有问题（泄漏、过拟合、冷启动）**根源都在数据**。
数据没弄对，后面调参全是白费。

### 阶段二：训练

| # | 做什么 | 命令 / 文件 | 为什么在这一步 |
|---|---|---|---|
| 9 | 装训练依赖 | `pip install -r requirements-ml.txt` | 和 CI 的依赖分开（见 README 说明） |
| 10 | 配 DagsHub 凭据 | `.env` 里的 `DAGSHUB_USER_TOKEN` | MLflow 要往远程记 |
| 11 | 先跑 baseline | 改 `CONFIG = BASELINE` 后 `python ml\train.py` | **先有对照，才知道改进有多大** |
| 12 | 再跑 tuned | 改 `CONFIG = TUNED` 后 `python ml\train.py` | 加目标编码特征 + 调超参 |
| 13 | 对比两个 run | DagsHub 网页 / `MlflowClient` | 决定哪个上生产 |
| 14 | 定版 | tuned 的 `save_to_app=True` → 覆盖 `app/model.joblib` | 应用读的就是这个文件 |

**为什么必须先跑 baseline**：没有 baseline 的"MAPE 14%"是个孤立的数字，
没法回答"这个模型到底值不值得用"。有了 51% 的对照，14% 才有意义。

### 阶段三：应用接入

| # | 做什么 | 文件 | 为什么 |
|---|---|---|---|
| 15 | 写推理封装 | `app/predictor.py` | 加载 joblib，按 `features` 顺序拼 ndarray |
| 16 | 暴露接口 | `POST /api/predict`（`app/routers/cars.py`） | 前端提交 → 返回价格 |
| 17 | 渲染结果页 | `templates/prediction.html` | 用户看得到 |
| 18 | 把模型打进镜像 | `Dockerfile` 的 `COPY app ./app` | 容器里不需要重新训练 |

**为什么推理代码要严格按 `payload["features"]` 的顺序拼**：
模型训练时输入是 ndarray，**列的顺序是有意义的**。顺序错了不会报错，
但会算出完全错误的价格。`model.joblib` 里存了 `features` 列表就是为了防这个。

### 阶段四：可追溯

| # | 做什么 | 为什么 |
|---|---|---|
| 19 | 每次训练 log git commit | 回答"哪个代码版本训练出这个模型" |
| 20 | log DVC 哈希 + 实际 md5 | 回答"哪个数据版本训练出这个模型"（并检查两者是否同步） |
| 21 | log 全部超参 | 回答"用什么配置训练的" |
| 22 | 存 `files/config.json` 制品 | 配置现在写在代码里，这份快照是它的历史记录 |
| 23 | 写 `ml/registry/current_model.md` | 回答"现在生产用的是哪个 run" |

**为什么这四个都要**：MLflow 的 run 是一次训练的快照。任何一项缺失，
半年后你都还原不出当时的环境。

## 13. 已知局限

诚实列出，避免误用。

### 13.1 冷启动失效

没见过车系的 MAPE ≈ 54.8%。**只能从下拉框选已知车系**，不能自由输入。

### 13.2 豪华车不准

100 万+ 的 MAPE 27.7%（MAE 25.86 万），只有 53 条样本。
模型对超跑/稀缺车型基本没有学习能力。

### 13.3 数据时效性

数据抓取于 2026 年 10 月。二手车价格随政策和市场波动，
**半年后模型就该重训**。`发布时间序号` 这个特征能吸收一部分时间漂移，但吸收不了全部。

### 13.4 缺少关键特征

真实定价还看：车况评级、事故记录、保养记录、所在城市、颜色、选装件…
这些**一个都没有**。这是数据源（公开列表页）的固有限制。

### 13.5 目标编码仍是近似方案

折内重算解决了大部分泄漏，但同一折内的样本仍有相关性。
更严格的做法是 `leave-one-out` 或加平滑（smoothing），当前没做。

### 13.6 原始爬虫数据已丢失

`data/爬虫/che168_wuhan_brands.csv` 被 `data/.gitignore` 忽略，也没进 DVC，
目前本地已不存在 → `ml/data_pipeline.py` **无法重新运行**。

**影响**：v1/v2 两个最终数据集还在（DVC 管理），所以**训练完全可复现** ✓
但"从原始爬虫数据重新生成数据集"这一步断了 ✗

**补救**：如果还能找回那个文件，放进 `data/爬虫/` 即可恢复；
或者把它也纳入 DVC 管理（`dvc add data/爬虫/che168_wuhan_brands.csv`）。
